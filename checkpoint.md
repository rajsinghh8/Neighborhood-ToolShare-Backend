## API conventions (decided)
- JSON field names snake_case exactly as in the spec. Success: POST 201 + entity body, GET 200, PUT 200 + entity, PATCH 200, DELETE 204 no body. List envelope `{items,total,page,size,limit,offset}` via send_page. List query params: page, size (alias limit), offset, sort, order(asc|desc) + filters. Bad sort field/enum/page value -> 422. Default size 20, max 100.
- PUT = partial-friendly update (only provided fields changed; use `.changes()`), validate merged result. Create requires required fields.
- Business-rule violations -> 422 (BusinessRuleError). Duplicate email -> 409. Not found / foreign event -> 404 (check event ownership FIRST via EventAccess, then the child's event_id match -> 404).
- Money out as "123.40" strings; ids ints; datetimes ISO `...Z`; dates `YYYY-MM-DD`.
- Auth: register 201 `{"id": n}` (email lower-cased, unique -> 409, password min 8 chars, name required); login 200 `{"access_token","token_type":"bearer","expires_in":1800}`; bad creds 401. Missing/invalid token 401.
- Event: create requires end_at > start_at (422), guest_capacity >= 0 int, budget >= 0. Event detail adds `accepted_guest_count` (int) and `budget_breakdown: {planned, actual, remaining}` where planned = event.budget, actual = sum of all expenses of event, remaining = planned - actual (can be negative). List/create/update responses use same base fields (list items without breakdown OK). Update: guest_capacity cannot go below current total guest count (422). Events are NOT audited.
- Task: statuses transitions allowed: pending->in_progress; in_progress->pending|completed; completed->in_progress; same->same is OK (no change). Illegal -> 422. Create: status default pending, any status accepted. depends_on_task_id must exist in same event (else 422), cannot be itself, no cycles (walk the chain) -> 422. Deleting a task sets dependents' depends_on NULL (FK). List sort: due_at, priority, status, id (priority sorted low<medium<high semantic: use CASE); filters status, priority. Audit: create/update/delete; if status changed -> STATUS_CHANGE (in addition to UPDATE when other fields changed too).
- Guest: capacity check on create: total guests + 1 > event.guest_capacity -> 422. invitation_status default pending. List filter invitation_status; sort id,name,invitation_status. On update where invitation_status changes: audit STATUS_CHANGE (+UPDATE if other fields changed) and notify event owner: NotificationType.GUEST_INVITATION_STATUS, message "Guest {name} changed invitation status to {status}", dedup_key `guest:{guest_id}:{new_status}:{uuid4hex}` (each change is a distinct source state). Email validated loosely (contains @) when given.
- BudgetCategory: planned_amount > 0... >= 0 ok; fields in responses: id,event_id,name,planned_amount; detail (and list items) add `actual_amount`, `remaining_amount` (planned-actual). Sort name, planned_amount, id. Duplicate names allowed.
- Expense: category must belong to event (422); amount > 0; filters startDate/endDate on incurred_on (inclusive); sort incurred_on, amount, id. Fields: id,event_id,category_id,description,amount,incurred_on. Update may change category (same rule).
- ScheduleItem: end_at > start_at (422); overlap (a.start < b.end and b.start < a.end, excluding self on update) -> 422. Date range filter: items whose start_at date within [startDate, endDate]. Sort start_at, id (default start_at asc).
- Vendor: fields id,event_id,name,service,total_amount; detail adds `total_paid`, `totalPaid`(same value), `outstanding`; sort name, id. Update total_amount below total paid -> 422. Vendor lookups: vendor must belong to event else 404.
- VendorPayment: amount > 0; sum(payments)+amount > vendor.total_amount -> 422 (exclude self on update); sort paid_on,amount,id. Fields id,vendor_id,amount,paid_on. Audited as AuditEntityType.VENDOR_PAYMENT with event_id of vendor's event.
- Notification: fields id,user_id,event_id,type,message,is_read,dedup_key,created_at; list for current user default sort created_at desc (sort allow: created_at,id,is_read), filter is_read=true|false; PATCH body `{"is_read": bool}` required; other user's -> 404. No create endpoint.
- AuditLog: GET only; fields id,event_id,actor_id,entity_type,entity_id,action,created_at; sort created_at,id default id desc; filters entity_type, action.
- Scheduler (`app/scheduler/notification_scheduler.py`): `NotificationScheduler(new_uow: Callable[[], UnitOfWork], topic: str)` with `async run_once(now: datetime|None=None) -> int` (naive UTC; returns number of notifications created) and `async run_safely()` (catches+logs everything; used by PeriodicCallback). Rules (recipient = event owner, skip completed tasks): due soon: now <= due_at <= now+24h -> TASK_DUE_SOON key `task_due_soon:{task_id}:{due_at.isoformat()}`; overdue: due_at < now -> TASK_OVERDUE key `task_overdue:{task_id}:{due_at.isoformat()}`; budget: category planned_amount > 0 and actual >= 0.9*planned -> BUDGET_THRESHOLD key `budget_threshold:{category_id}:{planned_amount}`. Each notification via NotificationRecorder in its own transaction (uses dedup).
- Kafka: audit events (topic eventforge.audit, via AuditRecorder) and notification events (eventforge.notifications) are published post-commit; consumer logs them. Disabled by default (KAFKA_ENABLED=false).
